飞书 IM 接入：Addons 自动订阅 + WebSocket 长连接

在桌面端扫一个码，就能在飞书里直接和 Agent 对话——不需要公网回调地址、不需要去开放平台手动配事件订阅和权限。本文记录完整实现路径、8 个踩过的坑，以及那个让「状态显示接收中却永远不回话」的核心 bug。

1目标与结论

要做成什么，以及最后做成了什么。

目标

让用户在桌面端 IM 面板点「扫码创建」，用飞书 App 扫码授权后，立刻就能在飞书里私聊/群聊这个 bot，消息交给本地 Agent 处理并把回复发回飞书。全程零手工配置：不填回调 URL、不填 encrypt_key、不去开放平台后台点事件订阅。

结论

做成了，靠两件事的组合：

  • Addons——把想要的权限和事件编码进二维码 URL，用户扫码创建应用的那一刻，开放平台就自动授予 im:message 权限并订阅 im.message.receive_v1 事件。
  • WebSocket 长连接——事件由开放平台主动推到本地建立的这条连接上，因此本机不需要公网可达，也就不需要回调地址和验签。
最终状态

桌面端 IM 面板显示 「已配置 · 运行中 · 接收中 · WebSocket 长连接」，飞书私聊发消息 Agent 正常回复。

2为什么不用 Webhook：一次关键的方向修正

最初的实现走的是 HTTP 回调，卡死在了「本地机器没有公网 IP」这个物理事实上。

第一版数据面是标准的 webhook 方案：起一个 /api/im/webhook/{id} 路由，做 AES 解密 + verification_token 校验，等飞书把事件 POST 过来。代码全部写完、单测全过，但真机永远收不到消息——因为飞书开放平台需要一个公网可达的 HTTPS 地址才能推送事件，而用户的桌面端跑在 127.0.0.1 上。这是架构问题，不是 bug，改代码解决不了。

转机来自对参考实现 grok-app 的逆向确认。原本以为它靠 Addons 实现「扫码即通话」，但在它的 remote-bridge/src 里全文搜索 addons 零命中。真正起作用的是这一句：

grok-app / remote-bridge（参考实现）TypeScript
lark.createLarkChannel({ appId, appSecret }).connect()  // ← WebSocket 长连接，不是 webhook

于是方案从「Addons 替代 webhook」修正为 「长连接负责收消息 + Addons 负责免手工配置」——两者解决的是不同问题，组合起来才是完整答案。

维度HTTP WebhookWebSocket 长连接
公网可达必须（本地开发的死穴）不需要，客户端主动外连
回调地址要在开放平台填并通过 challenge 校验无

经验

参考实现要看它实际调了什么，不要从功能名反推机制。这次如果不去 grep 一遍源码，会在 Addons 上继续投入而完全不解决收不到消息的问题。

3整体架构：从扫码到回复的完整链路

分两个阶段。阶段一只发生一次（创建），阶段二是每条消息都会走的运行时管线。

阶段一 · 扫码创建（一次性）

  • 1
    前端点「扫码创建」
    桌面端 IM 面板发起扫码请求，后端进入 scanFeishuBegin。
  • 2
    拿到 OAuth 设备码
    调飞书 device_code 接口，取回 device_code 与 verification_uri_complete（即二维码要编码的原始 URL）。
  • 3
    挂载 Addons ★ 关键
    把「要 im:message 权限 + 订阅 im.message.receive_v1 事件」这份声明 gzip 后 base64url 编码，作为 ?addons= 拼到 URL 上，再附 from=sdk&tp=sdk。
  • 4
    生成二维码，用户扫码 + App 内确认授权
    仅扫描不够，必须在飞书 App 里点确认，否则一直停在「等待扫码确认」。
  • 5
    开放平台按 Addons 自动配置应用
    创建应用的同时授予权限、订阅事件——这一步替代了原本要人工去后台点的所有配置。
  • 6
    轮询取回 app_id / app_secret → 自动启动
    前端以 enabled:true + connect_after_save:true 保存实例，SaveInstance 检测到后直接调 Start()，用户无需再点「启用接收」。

阶段二 · 运行时消息管线（每条消息）

  • 1
    飞书开放平台 ⇄ larkws.Client
    长连接由 SDK 维护，含握手、心跳、自动重连；应用层只注册事件处理器。
  • 2
    dispatcher.OnP2MessageReceiveV1 回调触发
    收到 im.message.receive_v1 事件。
  • 3
    归一化为 IncomingMessage核心 Bug 曾发生在这一步
    feishuEventToIncoming 提取文本、去掉 @ 占位符、忽略 bot 自身消息防回环，并写入 InstanceID——最初漏了这个字段，导致后面每一步都查不到东西。
  • 4
    Bridge.Deliver → 带缓冲的 inbox channel
    投递失败（队列满/未启用）只忽略错误，不阻断长连接循环，也不让 SDK 误判为处理失败而重推。
  • 5
    单条 dispatcher goroutine 串行消费 → handleMessage
    用 b.instances[msg.InstanceID] 查实例、b.transports[msg.InstanceID] 查回复客户端。
  • 6
    ACL 过滤 → 控制指令 → 交给 Agent
    默认全放行（私聊任意消息都触发）；/help /whoami /new /stop 直接短路处理；其余进入隔离会话，不污染桌面端主对话。
  • 7
    transport.ReplyText 把回复发回飞书
    20s 超时；失败时把错误写进实例的 LastError，前端面板可见。

4实现① · Addons：把配置编码进二维码

飞书官方 SDK 有这个能力但没有公开文档，编码格式是从官方 Go SDK 源码里逆向出来的。

官方实现位于 scene/registration/addons.go 的 encodeAddons，格式为 base64.RawURLEncoding(gzip(JSON))。注意是 RawURLEncoding（无 = 填充），用错会被开放平台拒绝挂载。

internal/im/qr.go新增
// defaultFeishuAddons 返回扫码时希望开放平台自动配置的权限与事件。
//   - scopes: 申请 im:message（收发消息）权限；
//   - events: 订阅 im.message.receive_v1 接收消息事件。
//
// 长连接接收不需要 HTTP 回调地址，因此 callbacks 留空。结构需与飞书官方
// SDK（scene/registration/addons.go）一致，否则开放平台会拒绝挂载。
func defaultFeishuAddons() map[string]any {
	return map[string]any{
		"scopes": map[string][]string{
			"tenant": {"im:message"},
		},
		"events": map[string]any{
			"items": map[string][]string{
				"tenant": {"im.message.receive_v1"},
			},
		},
	}
}

// feishuAddonsEncode 把 Addons 结构 gzip 压缩后用 base64url 编码，
// 与飞书官方 SDK（encodeAddons）的编码方式一致：base64.RawURLEncoding(gzip(JSON))。
func feishuAddonsEncode(addons map[string]any) (string, error) {
	body, err := json.Marshal(addons)
	if err != nil {
		return "", fmt.Errorf("marshal addons: %w", err)
	}
	var buf bytes.Buffer
	gz := gzip.NewWriter(&buf)
	if _, err := gz.Write(body); err != nil {
		_ = gz.Close()
		return "", fmt.Errorf("gzip addons: %w", err)
	}
	if err := gz.Close(); err != nil {   // 必须 Close 才会 flush 出完整 gzip 尾部
		return "", fmt.Errorf("gzip addons close: %w", err)
	}
	return base64.RawURLEncoding.EncodeToString(buf.Bytes()), nil
}

为什么 callbacks 留空

Addons 结构支持声明 callbacks（回调地址），但长连接模式下事件直接推到 WS 连接，不走 HTTP 回调，填了反而会让开放平台去校验一个不可达的地址。这是「两个方案组合」时最容易搞混的一点。

5实现② · WebSocket 长连接接收

新增 internal/im/feishu_ws.go，约 120 行。SDK 把脏活都干了，应用层只需注册处理器 + 做消息归一化。

internal/im/feishu_ws.go新文件
// feishuLongConn 持有单个飞书/Lark 实例的 WebSocket 长连接，用于接收
// im.message.receive_v1 事件。与 webhook 方式不同，长连接不需要公网回调地址、
// encrypt_key 或 verification_token —— 事件由开放平台直接推送到这条连接上，
// 因此本地运行也能正常收发（这正是 grok-app 的「扫码即通话」实现方式）。
type feishuLongConn struct {
	client     *larkws.Client
	channel    RemoteChannelID
	instanceID string
}

func newFeishuLongConn(instanceID string, channel RemoteChannelID, appID, appSecret string,
	deliver func(context.Context, IncomingMessage) error) (*feishuLongConn, error) {

	eventHandler := dispatcher.NewEventDispatcher("", "") // 长连接由飞书侧鉴权，无需验签
	eventHandler.OnP2MessageReceiveV1(func(ctx context.Context, event *larkim.P2MessageReceiveV1) error {
		if msg := feishuEventToIncoming(channel, instanceID, event); msg != nil {
			// 投递失败（队列满/未启用）不应让 SDK 把事件当作处理失败而重推，
			// 这里忽略错误，仅保证不阻断长连接循环。
			_ = deliver(ctx, *msg)
		}
		return nil
	})

	domain := feishuOpenBase(channel) // https://open.feishu.cn 或 https://open.larksuite.com
	client := larkws.NewClient(appID, appSecret,
		larkws.WithDomain(domain),
		larkws.WithEventHandler(eventHandler),
		larkws.WithLogLevel(larkcore.LogLevelError),
	)
	return &feishuLongConn{client: client, channel: channel, instanceID: instanceID}, nil
}

// run 会阻塞（SDK 内部的连接循环，自动重连），调用方应在独立 goroutine 中执行。
func (c *feishuLongConn) run(ctx context.Context) { _ = c.client.Start(ctx) }

// Close 关闭长连接并停止重连。
func (c *feishuLongConn) Close() { c.client.Close() }

归一化函数把 SDK 的事件结构翻译成项目内中立的 IncomingMessage，复用了 webhook 路径已有的 feishuMessageText / stripFeishuMentions，保证两条路径解析结果一致：

internal/im/feishu_ws.go · feishuEventToIncoming新文件
func feishuEventToIncoming(channel RemoteChannelID, instanceID string,
	event *larkim.P2MessageReceiveV1) *IncomingMessage {

	if event == nil || event.Event == nil {
		return nil
	}
	data := event.Event
	if data.Sender != nil && data.Sender.SenderType != nil {
		st := *data.Sender.SenderType
		if st == "bot" || st == "app" {
			return nil // 忽略机器人/应用自身消息，避免回环
		}
	}
	if data.Message == nil {
		return nil
	}
	msg := data.Message
	text := feishuMessageText(derefString(msg.MessageType), derefString(msg.Content))
	var mentions []feishuMention
	for _, m := range msg.Mentions {
		if m != nil {
			mentions = append(mentions, feishuMention{Key: derefString(m.Key)})
		}
	}
	text = strings.TrimSpace(stripFeishuMentions(text, mentions))
	if text == "" {
		return nil // 图片/文件等非文本消息直接跳过
	}
	chatType := derefString(msg.ChatType)
	if chatType == "" {
		chatType = "p2p"
	}
	userID := ""
	if data.Sender != nil && data.Sender.SenderId != nil {
		userID = derefString(data.Sender.SenderId.OpenId)
		if userID == "" {
			userID = derefString(data.Sender.SenderId.UserId)
		}
	}
	return &IncomingMessage{
		InstanceID: instanceID,   // ★ 缺这一行 = bot 永远不回话，详见第 7 节
		Channel:    channel,
		UserID:     userID,
		ChatID:     derefString(msg.ChatId),
		ChatType:   chatType,
		MessageID:  derefString(msg.MessageId),
		Text:       text,
		Mentioned:  len(msg.Mentions) > 0,
	}
}
SDK 全是指针字段

oapi-sdk-go 的事件模型每个字段都是 *string，直接解引用会 panic。统一加了个 derefString(s *string) string helper，nil 返回空串。

长连接要跟着实例的启停走，不能泄漏 goroutine 或连接。

7核心 Bug 剖析：显示「接收中」却永远不回话

这是整个过程中最难定位的问题——因为它不报任何错。

症状

扫码创建成功，面板显示 「feishu · 已配置 · 运行中 · 接收中」，last_error 为空。但在飞书里给 bot 发消息，没有任何反应：不回复、不报错、日志里也没有异常。

排查思路

「接收中」这个状态是由 b.longConns[id] 存在推导出来的——它只能证明连接对象建好了，不能证明消息真的流到了终点。所以问题一定在「事件到达」和「发出回复」之间的某一环。顺着管线读代码，在 handleMessage 的第一段找到了答案：

internal/im/runtime.go:220 · handleMessageBug 现场
func (b *Bridge) handleMessage(ctx context.Context, msg IncomingMessage) {
	b.mu.Lock()
	instance, ok := b.instances[msg.InstanceID]    // ← InstanceID 为 ""，查不到
	handler := b.handler
	transport := b.transports[msg.InstanceID]      // ← 同样查不到，为 nil
	b.mu.Unlock()
	if !ok || handler == nil || transport == nil {
		return                                     // ← 静默 return！不报错、不记日志
	}
	// ...

根因

长连接路径产出的 IncomingMessage 没有设置 InstanceID。feishuEventToIncoming 只填了 Channel / UserID / ChatID / Text 等，唯独漏了归属字段。而 handleMessage 是按 InstanceID 查表拿实例和回复客户端的：空 ID → 两个 map 都命中不了 → 走进那个 return → 消息被无声吞掉。

为什么 webhook 路径没这个问题？因为它在 HandleWebhook 里显式补了一行 msg.InstanceID = instanceID（runtime.go:369）——ID 是从 URL 路径 /api/im/webhook/{id} 里天然带出来的。新写的长连接路径没有这个「天然来源」，就漏掉了。

这类 bug 为什么难查

三个因素叠加：① 失败是静默的，防御性 return 吃掉了所有信号；② 状态指示器（「接收中」）监控的是连接建立而非端到端连通，给了虚假的安全感；③ 新旧两条路径共用下游，但上游契约（谁负责填 InstanceID）没有被显式表达，只存在于某一条路径的实现里。

修复

把 instanceID 一路透传到归一化函数内部，让「产出的消息一定带归属」成为函数自身的职责，而不是靠调用方记得补：

修复要点（3 处）Fix
// ① feishuLongConn 持有 instanceID
type feishuLongConn struct {
	client     *larkws.Client
	channel    RemoteChannelID
	instanceID string   // 新增
}

// ② 构造函数签名加上 instanceID，并传给归一化函数

		if msg := feishuEventToIncoming(channel, instanceID, event); msg != nil { ... }
	})
}

// ③ 归一化时写入（而不是在回调里补写，便于单测锁定）
return &IncomingMessage{
	InstanceID: instanceID,
	...
}

// 调用处 runtime.go:87

刻意没有选择在回调里 msg.InstanceID = instanceID 这种更省事的写法——放进 feishuEventToIncoming 内部才能被纯函数单测覆盖，从而写出回归测试锁死这个行为。

在 remote-bridge/src 全文 grep addons 零命中；它真正用的是 createLarkChannel().connect() 长连接。功能名和实现机制对不上。
解决
方案重新定位为「长连接收消息 + Addons 免手工配置」的组合，并向用户确认后执行。
P4Addons 编码格式无公开文档未知
症状
知道要传 ?addons=，但不知道内容怎么编码。
根因
官方文档未覆盖，只存在于 SDK 源码。
解决
临时克隆 larksuite/oapi-sdk-go 到本地，读 scene/registration/addons.go 的 encodeAddons，确认为 base64.RawURLEncoding(gzip(JSON))，实现等价编码器并写往返测试验证（编码→解码→比对 JSON 结构）。实现完成后删除临时克隆，依赖走 Go module cache。
P5编译失败：go.sum 缺条目构建
症状
missing go.sum entry：gogo/protobuf、gorilla/websocket（被 ws 包间接引入）。
根因
go get 只写了直接依赖，WS 传输层的间接依赖未落 go.sum。
解决
go mod tidy 补齐（gogo/protobuf v1.3.2、gorilla/websocket v1.5.0），go build ./... 通过。
P6单元测试真连外网 + 断言过时测试
症状
TestStartStopControlsReceiving 失败，日志里出现真实 API 报错 1000040346: app_id is invalid（假凭据打到了飞书线上）。
根因
① Start() 会真的拉起 WS goroutine 去连接；② 断言仍在期望 TransportWebhook，而实现已改为 longconn。
解决
加 disableLongConn 测试开关，Start() 里 if !b.disableLongConn { go lc.run(ctx) }，保证单测无外部依赖；断言同步改为 TransportLongConn。
P7状态「接收中」但 bot 不回消息核心
症状
一切状态正常、无报错，发消息石沉大海。
根因
长连接路径产出的消息 InstanceID 为空，handleMessage 按 ID 查 instances/transports 全部落空，走进防御性 return 被静默丢弃。
解决
透传 instanceID 至 feishuEventToIncoming 并写入消息；新增 3 个回归测试锁定。详见第 7 节。
P8重建 Go 后端失败：文件被占用环境
症状
go build -o bin/LongCat-frontend.exe 报权限/占用错误，无法覆盖。
根因
正在运行的 Tauri 桌面端把 Go 后端作为子进程拉起，进程锁住了该 exe。
解决
重建前先 taskkill /IM LongCat-frontend.exe /F 与 taskkill /IM longcat-frontend-desktop.exe /F。这是 Windows 上的固定前置步骤，已记入项目备忘。

重新构建的正确顺序

Windows / Git Bash流程
# 1. 必须先停掉运行中的桌面端，否则 bin/ 里的 exe 被子进程锁住（P8）
taskkill /IM LongCat-frontend.exe /F
taskkill /IM longcat-frontend-desktop.exe /F

# 2. 重建 Go 后端（真正承载 IM 逻辑的部分）
go build -o bin/LongCat-frontend.exe ./cmd/LongCat-frontend

# 3. 重建 Tauri 桌面壳（Rust 源码没改时可跳过，重启即可生效）
cd desktop/src-tauri && cargo tauri build

桌面壳启动时通过 find_backend() 定位并拉起 bin/LongCat-frontend.exe serve -addr 127.0.0.1:5510，WebView 加载该地址。所以 IM 相关改动只需重建 Go 后端 + 重启桌面端，不必每次都重编 Rust。

11遗留事项

R1安装包不含 Go 后端二进制遗留 · 非本次引入
问题
tauri.conf.json 没有配置 externalBin，MSI / NSIS 安装包里只有 icon，不包含 LongCat-frontend.exe。干净机器上安装后启动会因 find_backend() 找不到后端而失败。
现状
开发/测试直接运行 target/release/longcat-frontend-desktop.exe 或 cargo tauri dev 均正常（能在仓库 bin/ 下找到后端）。
方案
加 externalBin 配置 + 构建期拷贝 Go 二进制，即可产出自包含安装包。
R2缺少运行时可观测性改进建议
问题
P7 之所以难查，就是因为管线中途没有任何信号。handleMessage 的防御性 return 会吞掉所有异常输入。
建议
① 在该 return 前记一条 warn 日志（打印 InstanceID / ChatID）；② 面板状态区分「已连接」与「已收到过消息」，例如显示最近一次收发时间戳；③ 记录回复接口的返回码，便于区分「没收到」和「回复被拒」。
R3Addons 权限键的兼容性待观察
问题
当前申请的是 im:message。不同类型的应用（个人应用 / 企业自建）对权限键的接受度可能不同。
备选
若某些账号下被拒，可改用 im:message:send_as_bot 或组合键。当前账号已验证可用。
