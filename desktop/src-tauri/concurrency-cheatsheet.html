五条设计原则 Principles
1
用 channel 通信，用锁保护状态。流式/事件走 channel；map 与共享字段走 Mutex/RWMutex，各司其职。
2
跨 goroutine 发送永不阻塞。所有发送都是 select + ctx 取消或 default 兜底，从源头杜绝 goroutine 泄漏。
3
context 贯穿取消链。HTTP 请求 → Session.Stream → LLM 请求 → 工具执行，取消一路透传。
4
串行消费替代加锁。IM dispatcher 单 goroutine 消费，Session 保持非并发安全无需改造。
5
channel 只由唯一方关闭，停止都有超时兜底。defer close + sync.Once 杜绝 double-close；shutdownTimeout 2s 兜底优雅退出。

为什么 StreamEvent channel 缓冲 32？

          
点击翻转 ▸

        
参考答案
    
          
  • 有界缓冲 = 背压：生产者（LLM 流式输出）快于消费者（SSE flush）时，缓冲吸收抖动。
    • 
          
  • 缓冲有限 → 满时 sendEvent 的 select 会让生产者等消费者，天然限速，不会无限堆积内存。
    • 
          
  • 太大浪费内存，太小频繁阻塞；32 是「每轮工具事件 + 若干 delta」的合理量级。
    • 
          
  • 面试延伸：无缓冲 channel（stream_test.go:25）专门用来测「发送阻塞 + 取消解锁」。

sendEvent 解决了什么问题？

          
点击翻转 ▸

        
参考答案
    
          
  • goroutine 泄漏：裸 `out <- ev` 在消费者断开/不再读取时永久阻塞，生产者永远退不出。
    • 
          
  • select 同时监听 ctx.Done：消费者一断开（HTTP 连接关闭 → r.Context 取消），生产者立即 return。
    • 
          
  • 配合 defer close(out)：即使 panic，消费者侧 range 也能正常收尾。
    • 
          
  • 这是本项目所有跨 goroutine 发送的统一纪律：发送永不阻塞。

为什么锁要拆成 cancelMu / mu / imMu 三把？

          
点击翻转 ▸

        
参考答案
    
          
  • 一把大锁会把不相关的临界区串行化：桌面端长对话占着锁时，IM 消息、取消操作全排队。
    • 
          
  • cancelMu 只保护 cancel 函数赋值（server.go:874-880）；mu 串行化桌面对话；imMu 隔离 IM 会话。
    • 
          
  • 锁粒度越细，并发度越高，但死锁面越大——本项目按「临界区是否相关」拆，而不是按字段数拆。
    • 
          
  • 面试延伸：多把锁要约定一致的加锁顺序防死锁。

singleflight 解决什么？在哪里用的？

          
点击翻转 ▸

        
参考答案
    
          
  • 解决缓存击穿：N 个并发请求同一缺失 key，若各自去加载，上游被打爆。
    • 
          
  • cache.GetOrLoad（cache.go:130-156）：第一个请求执行 loader，其余通过 `<-f.done` 等共享结果。

    • 
          
  • 关键实现点：inflight 表用完必删 + close(f.done) 唤醒所有等待者，无泄漏。

设计
          
令牌桶 vs 漏桶的区别？

          
点击翻转 ▸

        
参考答案
    
          
  • 令牌桶：匀速补令牌、可突发消费（桶容量 = 突发上限），允许「攒一波突发」。本项目用的这种。
    • 
          
  • 漏桶：匀速漏水，请求进桶排队，严格限速、不允许突发。
    • 
          
  • 选型：LLM API 通常允许一定突发（TPM/RPM 配额有窗口），令牌桶更贴合；本项目默认 10 req/s。
    • 
          
  • 实现差异：漏桶通常用队列 + 定时出队，令牌桶用「容量 channel + 定时补令牌」。
