一、实现概览

重试与限流都收敛在 LLM 层唯一的 HTTP 出口，因此 OpenAI Chat / Responses、Anthropic、Ollama 四套协议与 SSE 流式调用一处改动全覆盖，上层 Agent / UI 完全无感。

代码位置

resilience.go 重试配置 + 令牌桶限流器
protocols.go postJSON 重试循环 + 限流等待
resilience_test.go 5 个单测

分层职责

重试 传输边界 postJSON
限流 出向（我们→供应商），当前全局令牌桶可配
演进 更优解：上提 Manager 做 per-provider 桶（已设计未实现）
核心设计哲学：把"重试消化失败 + 限流抑制失败"放在 LLM 边界，让上层只面对稳定的语义，外部世界的不整齐与不稳定都挡在边界之内。

请求流转

postJSON(ctx, url, headers, body)
   └─ waitRateLimit(ctx)              # 出向限流：取一个令牌
   └─ httpClient.Do(req)
        ├─ 网络错误 / 429 / 5xx  ──→ 退避(sleepWithCtx) ──→ 重试（最多 MaxAttempts-1 次）
        └─ 2xx                  ──→ 返回 *http.Response（交给上层解析）

二、重试（Retry）传输边界

触发条件

  • HTTP 状态码：429 Too Many Requests、500、502、503、504
  • 网络错误：连接重置、超时、DNS 失败（err != nil 且未拿到响应）
  • 不重试：4xx 客户端错误（400/401/403/404 等，重试无意义）

退避策略

MaxAttempts 3（1 首发 + 2 重试）
BaseDelay 500ms
MaxDelay 8s
MaxRetryAfter 30s
退避公式 BaseDelay × 2^attempt
抖动 全抖动 0..d，防惊群
Retry-After 优先采用（秒 / HTTP-date）
取消 退避期间 ctx 取消立即返回

关键代码

// 可重试的状态码
func retryableStatus(code int) bool {
    switch code {
    case http.StatusTooManyRequests, // 429
        http.StatusInternalServerError, // 500
        http.StatusBadGateway,          // 502
        http.StatusServiceUnavailable,  // 503
        http.StatusGatewayTimeout:       // 504
        return true
    }
    return false
}

// 退避：优先 Retry-After，否则指数退避 + 全抖动
func backoff(rc RetryConfig, attempt int, resp *http.Response) time.Duration {
    if resp != nil {
        if ra := resp.Header.Get("Retry-After"); ra != "" {
            if secs, err := strconv.Atoi(ra); err == nil {
                d := time.Duration(secs) * time.Second
                if d <= rc.MaxRetryAfter { return d }
                return rc.MaxRetryAfter
            }
            if t, err := http.ParseTime(ra); err == nil {
                if d := time.Until(t); d > 0 && d <= rc.MaxRetryAfter { return d }
            }
        }
    }
    d := rc.BaseDelay * time.Duration(1<<uint(attempt))
    if d > rc.MaxDelay { d = rc.MaxDelay }
    if d <= 0 { return 0 }
    return time.Duration(rand.Int63n(int64(d))) // 全抖动
}

// 退避等待可被 ctx 取消打断
func sleepWithCtx(ctx context.Context, d time.Duration) error {
    if d <= 0 { return nil }
    t := time.NewTimer(d)
    defer t.Stop()
    select {
    case <-t.C: return nil
    case <-ctx.Done(): return ctx.Err()
    }
}
流式边界：SSE 响应一旦开始读取便不再重试，仅对"连接建立 / 首字节前"的失败重试——避免重复下发已展示的 token。

三、限流（Rate limiting）出向 · 令牌桶

重试兜住瞬时失败，限流从源头降低被限流的概率。采用零依赖令牌桶，在每次请求发起前先取令牌。

行为

默认 10 请求/秒（突发容量同为 10）
可调 SetRateLimit(rps)
关闭 SetRateLimit(0)
方向 client-side 出向（我们→供应商）

为什么不用 x/time/rate

项目约定"能用标准库就用标准库、避免为小特性加依赖"。令牌桶几十行可控，且要的是可取消 Wait + 简单突发。

关键代码（令牌桶）

// 每秒 rps 个令牌、突发容量为 rps；rps<=0 表示不限流
func NewLimiter(rps int) *Limiter {
    if rps <= 0 { return &Limiter{capacity: 0} }
    l := &Limiter{
        tokens:   make(chan struct{}, rps),
        stop:     make(chan struct{}),
        capacity: rps,
        ticker:   time.NewTicker(time.Second / time.Duration(rps)),
    }
    for i := 0; i < rps; i++ { l.tokens <- struct{}{} }
    go func() {
        for {
            select {
            case <-l.stop: return
            case <-l.ticker.C:
                select { case l.tokens <- struct{}{}: default: } // 桶满丢弃
            }
        }
    }()
    return l
}

func (l *Limiter) Wait(ctx context.Context) error {
    if l == nil || l.capacity <= 0 { return nil }
    select {
    case <-l.tokens: return nil
    case <-ctx.Done(): return ctx.Err()
    }
}
演进方向：当前是"出向全局桶"，对 OpenAI 和本地 Ollama 用同一速率并不合理。更优解是上提到 Manager 做 per-provider 令牌桶：每个 Provider 带自己的 Limiter，热切换时配额随之切换，优先级路由也能在路由层区分。这是已设计、尚未实现的方案。

四、面试问题 & 参考答案

点击展开每条。建议先自己答一遍，再对照参考答案。

Q1. 重试放在哪一层？为什么放在传输边界 postJSON，而不是 Manager？

答：重试是"HTTP 调用失败再试一次"，属于传输层韧性，与协议、供应商无关。放在唯一的 HTTP 出口 postJSON，对四套协议和 SSE 流式零侵入全覆盖，上层 Agent / UI 完全无感。

Manager 层更适合放"供应商策略 / 配额 / 路由"这类业务概念，不应耦合传输重试的细节。把重试下沉到边界，也符合"让核心 loop 只面对稳定语义"的适配器哲学。

Q2. 为什么用指数退避 + 全抖动（full jitter），而不是固定间隔？

答：指数退避让重试间隔随失败次数增长，给服务端恢复时间；全抖动（0~d 随机）避免大量并发请求在同一时刻同时重试，造成"重试风暴 / 惊群效应"。固定间隔或同步重试在高并发下会周期性地集中打爆服务端。

Q3. 服务端返回 429 且带 Retry-After，你怎么处理？

答：backoff 优先解析 Retry-After：若是秒数直接转 time.Duration；若是 HTTP-date 用 http.ParseTime 算差值。两者都受 MaxRetryAfter = 30s 上限约束，防止服务端给一个超大值导致请求长时间挂起。其余情况才用指数退避兜底。

Q4. 流式（SSE）响应中途失败了，为什么不整段重试？

答：流一旦开始已经向用户 emit 了 token，全量重试会重复下发已展示的内容、造成混乱，且无法安全"续传"。因此只对"连接建立 / 首字节前"的失败重试；流中途断则向上抛错，由上层决定是重试整轮对话还是提示用户。

Q5. 限流为什么做在 client-side 出向，而不是 server-side 入向？

答：痛点是"供应商返回 429"，根因是我们打得太快，所以要在出向（我们→供应商）节流，从源头降低 429。

server-side 入向限流是防本地 Web / TUI 打爆自己，场景不同。当前 server 只监听 127.0.0.1，入向暴露面小，优先级低；若要做，是在 local() 中间件外层挂一道令牌桶。

Q6. 不同供应商配额不同（OpenAI vs 本地 Ollama），一个全局令牌桶够吗？

答：不够。全局桶会把 Ollama（基本无限）也错误限速，也对不齐各家 RPM / TPM。

更优解是上提 Manager 做 per-provider 令牌桶：每个 Provider 带自己的 Limiter，热切换时配额随之切换，优先级路由也能在路由层区分。这是已设计、尚未实现的演进方向——被追问时这样答，反而体现架构判断。

Q7. 退避等待期间如果用户点了"停止"（ctx 取消）会怎样？

答：sleepWithCtx 用 select 同时监听 timer.C 和 ctx.Done()。ctx 取消会立即返回 ctx.Err()，不会傻等完整个退避，用户停止操作能立刻中断。

Q8. 重试会不会造成重复副作用（重复写文件 / 重复发消息）？

答：当前重试只作用于只读的对话补全请求（POST 到 LLM，本质是幂等查询），不重试带副作用的工具调用——工具执行在 Agent 层，不在 postJSON 重试范围。

若未来要对写类 API 重试，需要服务端幂等键（idempotency-key）配合。能主动提到"幂等性"是这题的加分点。

Q9. 为什么零依赖，不用 golang.org/x/time/rate？

答：项目约定"能用标准库就用标准库、避免为小特性加依赖"。令牌桶几十行就能写，且更可控（我们要可取消的 Wait + 简单突发）。当然 x/time/rate 更完备，需求变复杂时可平滑切换。

Q10. 你是怎么测试重试和限流的？

答：resilience_test.go 用 httptest 起服务：

  • 前 N 次返回 429 / 503、之后 200 → 断言重试后成功，且服务端被调用次数 = 尝试次数；
  • 始终 503 → 断言返回 503 且调用次数 = MaxAttempts；
  • 限流器测试：令牌耗尽后 Wait 在 ctx 超时返回错误；NewLimiter(0) 时立即返回（关闭限流）。
